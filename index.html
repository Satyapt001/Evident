01 / Why

Alerts without context slow investigations

Network anomalies, phishing links, suspicious emails, manipulated media and unknown files are often analysed in separate tools. Analysts then reconcile the results by hand and interpret alerts without enough supporting evidence.

CyberShield is designed to move from isolated detectors toward one explainable investigation workflow: each finding carries its evidence, feeds a shared risk view, and ends in a recommended next step for a person to review.

These are design objectives for the project, not claims about other products.

02 / Capabilities

Core capabilities

Six analysis areas intended to share one dashboard. Select a card to see more.

Network Anomaly and Technical Behaviour Detection

Analyses network-flow features and relevant technical telemetry for suspicious patterns.

Findings are presented with the features that contributed, so analysts can judge them rather than trust a bare score.

Phishing and URL Analysis

ML-based URL classification and available threat-intelligence enrichment.

Enrichment depends on the threat-intelligence sources available at deployment.

Social Engineering and Email Analysis

Analyses email text for configured indicators such as urgency, impersonation, credential-harvesting language and suspicious requests.

Indicators are configurable and shown alongside the text that triggered them.

Deepfake and Digital-Impersonation Analysis

Analyses submitted media for potential manipulation indicators using the project's image-analysis approach.

Results indicate potential manipulation. They are not proof of authenticity or forgery.

Malware Triage

Supports initial suspicious-file analysis and severity assessment.

Triage helps prioritise files for deeper analysis. It does not replace it.

Risk Assessment and Response Recommendations

Presents available risk information, evidence, explanations, incidents and recommended next steps for analysts.

Recommendations are suggestions for a security administrator or SOC analyst to review.

Implementation status: the capability descriptions above are project objectives. Check the GitHub repository for what is implemented and tested. Live-feed, automation and backend integration work is still in progress.

03 / Workflow

From detection to recommended response

The intended six-stage flow. Scroll or select a stage. End-to-end automation depends on integration work that is still in progress.

  1. Receive or submit relevant digital evidence.

  2. The appropriate detector produces a finding.

  3. Available results and evidence inform severity.

  4. Display the indicators that support the finding.

  5. Surface relevant findings for investigation and tracking.

  6. Provide suggested actions for the security administrator or SOC analyst.

05 / Approach

Intended design approach

  • One interface

    Multiple threat surfaces in a single view.

  • Connected workflow

    From detection to recommended response.

  • Evidence first

    Explanations instead of only binary results.

  • Analyst in the loop

    Recommendations a person reviews and decides on.

  • Modular

    Detectors plug into a shared dashboard.

No detection accuracy, false-positive rate or remediation guarantee is claimed.

Steps

  1. Clone the repository

    Open PowerShell where you want the project.

    git clone https://github.com/Satyapt001/Evident.git
cd Evident

  2. Create the backend environment

    Python 3.11 virtual environment, then dependencies. Use the requirements file the repository maintains: backend\requirements.txt, or requirements.txt in the root. Do not install both.

    py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip setuptools wheel
pip install -r .\backend\requirements.txt
python -m pip check

    If activation is blocked, run Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass for the current terminal only, then activate again.

  3. Configure environment variables

    If the repository has an .env.example, copy it and fill in the values the backend actually reads. Do not invent variable names. Never commit .env or real secrets.

    Copy-Item .env.example .env
# or, if the template is in the backend folder:
Copy-Item backend\.env.example backend\.env

  4. Install Sysmon (Windows live telemetry)

    Starting the backend or frontend does not install or start Sysmon. It is a separate Windows service and needs an Administrator terminal.

    Download Sysmon from the official Microsoft page and extract Sysmon64.exe (for example to C:\Tools\Sysmon). Check whether the project ships a reviewed Sysmon configuration first; if not, use this basic one, replacing the schema version with the value printed by Sysmon64.exe -s.

    cd C:\Tools\Sysmon
.\Sysmon64.exe -s
notepad .\cybershield-sysmon.xml
    <Sysmon schemaversion="REPLACE_WITH_SUPPORTED_SCHEMA_VERSION">
  <EventFiltering>
    <NetworkConnect onmatch="exclude" />
  </EventFiltering>
</Sysmon>
    .\Sysmon64.exe -accepteula -i .\cybershield-sysmon.xml
Get-Service *Sysmon*
Get-WinEvent -FilterHashtable @{ LogName = "Microsoft-Windows-Sysmon/Operational"; Id = 3 } -MaxEvents 10

    Event ID 3 records network connections. It is not a packet capture. If no events appear, browse a website and run the last command again. To change the configuration later: .\Sysmon64.exe -c .\cybershield-sysmon.xml.

  5. Start the backend

    In a normal PowerShell terminal at the project root. Keep it open.

    .\.venv\Scripts\Activate.ps1
$env:PYTHONPATH = "$(Get-Location)\backend;$(Get-Location)"
python -m uvicorn app.main:app --app-dir ".\backend" --host 127.0.0.1 --port 8000 --reload

    Check http://127.0.0.1:8000/docs. The network model health endpoint is /api/v1/analyze/network/health; it depends on the model artifacts being present.

  6. Verify Sysmon telemetry

    With Sysmon and the backend both running, in a second terminal:

    Invoke-RestMethod `
    -Uri "http://127.0.0.1:8000/api/v1/telemetry/sysmon/events" `
    -Method GET

    No events? Check the Sysmon service, that Event ID 3 is enabled, the Windows event log contents, the backend terminal output, and that the account running the backend may read the Sysmon event log.

    A Sysmon event is an observation, not an AI-classified threat. Model-based network evaluation is a separate operation, and raw events are not model predictions. The dashboard polls about every five seconds, which does not mean Sysmon produces an event that often.

  7. Start the frontend

    In another terminal. Use npm install instead of npm ci if there is no package-lock.json.

    cd frontend\cybergurad-dashboard
npm ci
npm run dev

    Open http://localhost:5173 (or the address Vite prints). If the dashboard shows no data, check that the backend is running, the API base URL is http://127.0.0.1:8000, CORS allows the frontend origin, and the browser Console and Network tabs.

  8. Daily startup and shutdown

    Dependencies are installed once. Afterwards: make sure Sysmon is running (Get-Service *Sysmon*), start the backend as in step 5, then run npm run dev in the frontend folder. Stop either server with Ctrl+C and leave the environment with deactivate. Sysmon keeps running independently, including after a restart. To stop it: Stop-Service Sysmon64 (use the name shown by Get-Service).

Linux and macOS

The backend and frontend can run on Linux or macOS with compatible Python and Node.js. The Sysmon live feed is Windows-only; other systems need a separate supported telemetry collector and integration.

git clone https://github.com/Satyapt001/Evident.git
cd Evident
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r backend/requirements.txt
export PYTHONPATH="$PWD/backend:$PWD"
python -m uvicorn app.main:app --app-dir ./backend --host 127.0.0.1 --port 8000 --reload
# second terminal
cd Evident/frontend/cybergurad-dashboard && npm ci && npm run dev

08 / FAQ

Frequently asked questions

What is CyberShield?

An AI-powered cyber threat, phishing and digital impersonation detection and response system that aims to combine several analysis capabilities in one analyst workflow.

What types of threats can it analyse?

Network anomalies and technical behaviour, phishing URLs, social-engineering emails, deepfake and impersonation media, and suspicious files (malware triage).

Who is the intended user?

Organisations and general users, and technical users such as IT teams, security professionals, SOC analysts and security administrators.

How does the detection-to-response workflow operate?

Evidence is submitted, a detector classifies it, risk is assessed, supporting indicators are explained, relevant findings become alerts or incidents, and suggested actions are offered for review. Integration work for this flow is ongoing.

Does CyberShield automatically take remediation actions?

No automatic remediation is claimed. Recommendations are suggestions for a person to review. Any automated action would be a separate capability.

Is the GitHub repository available yet?

Yes. The project is on GitHub. Check the repository for the current state of each capability.

Is the backend integrated with this landing page?

No. This page is static and shows no live data. The FastAPI backend and dashboard are in the repository and are installed separately.

How can I install CyberShield when the source is released?

Follow the Install section of this page, and check the repository files first. Live Windows telemetry also needs Sysmon, which is installed separately.
